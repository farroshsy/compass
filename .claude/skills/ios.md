# iOS rules

Swift 6 language mode, strict concurrency, iOS 18 minimum. SwiftUI and
Observation. One SPM package plus a thin `App/` folder, generated by xcodegen.

- **No `await` between the tap and the pixel. No `await` between the tap and
  durability.** If you are adding one, you are breaking the product.
- **No network call on the launch path.** Ever, for any reason.
- The tap path is, in order: apply to projection, fire haptic, append
  synchronously to the journal — all three synchronous — then two detached
  `Task`s for the actor and the achievement engine.
- First frame renders from a synchronously-read snapshot. Full replay happens in
  a `.task` afterwards and reconciles. If they disagree, the replay wins and the
  snapshot is rewritten.
- Four **in-process** concurrency boundaries and no more, plus exactly one
  cross-process boundary once the widget exists (see below):
  `@MainActor` for the model and UI;
  `actor EventLog` for the file; `nonisolated` pure functions for projection,
  streak and achievement evaluation; plain `Sendable` structs for networking.
- The model is `@MainActor @Observable final class`. It is **not** an actor —
  Observation cannot synchronously observe state across an actor hop, and the
  hop lands in the tap path.
- Do not wrap `URLSession` in an actor. It is already concurrency-safe.
- Every path gets its base URL from a **single injected `storeURL`**; construct a
  file path nowhere else. Moving that URL to
  `FileManager.containerURL(forSecurityApplicationGroupIdentifier:)` is then one
  line, and it **must happen before the widget ships in week 2**. It is not a
  rewrite, and it must not be used to gate week-1 storage code on a paid account.
- The container is `NSFileProtectionCompleteUntilFirstUserAuthentication` — the
  strongest class a locked-screen widget can read. iCloud device backup is
  **deliberately left enabled**; it is the only backup until CloudKit exists.
- **The widget is a second writer with its own `device` UUID and its own `prev`
  chain.** Never share a *chain* across processes — `Synchronization.Mutex` does
  not span processes. One event per `write(2)` to an `O_APPEND` descriptor;
  advisory `flock` around any read-tail-then-append, and around the identity mint.
  Ship the two-writer test *with* the widget, not after. **Shipped in week 2, and
  it found a real ordering defect the day it was written** — see the `lamport`
  rule in `.claude/skills/architecture.md`.
  - This line used to say "its own `lamport` sequence" too, and that was the
    defect. The **chain** is per writer; the **clock** is shared, resumed from the
    highest `lamport` anywhere in the log. A second writer starting at 1 has every
    event outranked by the first writer's.
  - **One writer name can be several processes.** iOS may run multiple widget
    extension instances and all of them are `WriterIdentity.widget`. What keeps
    that safe is that the widget's journal is single-use — open, record one event
    under the lock, close — and that the identity is minted under the same lock.
    Do not hand the widget's journal a resume: that is what makes `record` skip
    the lock.
- **The app must re-read when it comes back.** `TodayView` reconciles on
  `.task(id: scenePhase)`, not on a plain `.task`, because a second process can
  have written while the app was in the background. It also re-primes the clock.
- Build App Intents first, as substrate — but ship **only the widget** on top of
  them in v1. No `AppShortcutsProvider` phrases, no Control Center control, no
  Action Button until the triggers in `docs/technical.md` §10 actually fire.
  Only the widget serves the three-second loop; every other entry point is one
  more place a wrong day boundary or a lost write can hide. Set
  `isDiscoverable = false` on the intent — that is the one place the deferral can
  actually be enforced rather than remembered.
- **An app extension needs `MARKETING_VERSION` and `CURRENT_PROJECT_VERSION`, and
  they must match the host's.** Set once at the project level in `project.yml`. An
  app installs on the simulator without them; an extension is refused with "Failed
  to create app extension placeholder".
- The day boundary is 04:00 local, applied once when the event is created, never
  in the fold.
- **Copy** `Seal.swift` and `Calendar.swift` from the `before` repository into
  `Sources/CompassInfrastructure/`, with an attribution header. Not an SPM path
  dependency, not a submodule — that folder can move and take the build with it.
  Do **not** copy `Log.persist()` at all; it rewrites the whole array per append.
  - **Both are copied in as of week 4, and `Calendars.anchor(_:)` was fixed while
    copying, not after.** It returned "the first proof a calendar returns" and
    discarded the other two, which ADR 0004 forbids in those words. The
    replacement returns one result per calendar and the caller keeps all of them.
    A fix made during a copy is a fix; a fix promised for later is a defect that
    ships.
- `Signer.sign(_ text:)` double-hashes (`SHA256(SHA256(text))`). Self-consistent
  in its own app, but **never call it on the achievement path.** The convention
  is fixed in `docs/achievement-protocol.md` §6.7: sign `canonicalBytes`
  directly with the `DataProtocol` overload, so the signed message is `digest`
  with no second hash.
- `Signer` as inherited **cannot restore an enclave key across launches** — it
  mints a fresh one every construction and has no `init(enclaveKeyData:)`. Fix
  that when copying, or every launch has a different public key. `technical.md`
  §8, `memory/known-bugs.md`.
- Record `Signer.backing` honestly. A simulator-made proof must never look as
  strong as a phone-made one.
- **The signing key is persisted and restored, and the test drives the real
  keychain.** `KeychainStore` takes an injectable service name so a test can own
  one and delete it. A fake behind a protocol would make "the key survives
  relaunch" pass while the two `SecItem` calls that decide it went unexercised.
- **Resources that must be readable under `swift test` are loose files, not asset
  catalogues.** `swift build` does not run `actool`, so a `.xcassets` is copied
  verbatim into the bundle and every lookup inside it fails on macOS — which
  turns a guard into a vacuous pass. And **never name a resource directory
  `Resources`**: `codesign` reads that as a macOS bundle layout and refuses the
  iOS resource bundle with "bundle format unrecognized".
- Anchoring retries with exponential backoff via `BGProcessingTask` **and**
  drains the pending queue opportunistically on launch. Both. `BGProcessingTask`
  carries no execution guarantee and the UI is forbidden to show anchoring
  failure, so the scheduler path alone can fail undetectably; the launch drain
  is also the only one observable in a test. `docs/technical.md` §9.8.
  - **Shipped in week 4.** The launch drain is `await`ed inside
    `TodayModel.reconcile()` — the `.task` that runs *after* the first frame —
    and not dispatched into a detached `Task`, because a detached task is a race
    a test can only sleep through. **A drain with nothing due makes no network
    request at all**, which is what makes it safe to run on every foreground
    rather than only on a cold launch. That property is a test, not a hope.
  - **The backoff needs no new field.** `Attestation` has no attempt count and
    week 4 did not add one: both anchor files are append-only, so the number of
    `failed` lines *is* the counter. Do not add a field to the protocol to hold a
    number the file already holds.
- **An array-valued Info.plist key cannot be set with `INFOPLIST_KEY_`.** The
  generated-plist mechanism knows a fixed set of keys and **silently drops the
  rest** — no warning, at any stage. `BGTaskSchedulerPermittedIdentifiers` and
  `UIBackgroundModes` were written that way first and were simply absent from the
  built product; `BGTaskScheduler.register` throws when its identifier is
  missing, and `.claude/skills/ui.md` forbids that failure from being visible
  anywhere, so the app would have looked completely normal. The app target now
  carries a real `App/Info.plist` that merges over the generated one, the same
  arrangement the widget target already used. **Check the built
  `Info.plist` with `plutil -p` rather than the build settings that were meant to
  produce it.**
- Never let the app become unusable because iCloud is signed out, the network is
  down, or an anchor failed. Test those paths.
- Install via TestFlight with a paid developer account. A free profile expires in
  seven days, and an app that uninstalls itself weekly is not a habit. **A
  TestFlight build expires 90 days after upload** and then refuses to launch, so
  a build gets uploaded every quarter — a standing obligation, not a one-off.
- **Never resolve an expired build by deleting and reinstalling.** Update in
  place. Deleting the app destroys the App Group container and the entire log.
  Verify a recent off-device export exists before touching the installation.
