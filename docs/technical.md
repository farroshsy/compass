# Compass — technical

This document states the stack, the data model, the flow of an event, storage,
sync, auth, contracts, what is scheduled, and what is deferred. §10 keeps those
last two apart: **scheduled** items are decided and wait only on sequence;
**deferred** items each carry the trigger that would make them worth building.
An item that is neither — no date and no trigger — is refused, and belongs in
the non-goals in `docs/product.md`.

Related: `docs/achievement-protocol.md` fixes the on-disk format of an
achievement. `docs/adr/` holds the four decisions with real alternatives.

---

## 1. Stack

| Layer | Choice | Note |
|---|---|---|
| Language | Swift 6, strict concurrency, language mode 6 | |
| UI | SwiftUI + Observation (`@Observable`) | No UIKit unless forced |
| Minimum OS | iOS 18 | Needed for `Synchronization.Mutex` and `ControlWidget` |
| Build | One SPM package + thin `App/` folder, generated by xcodegen | Same shape as the existing Shipped app |
| Persistence | Append-only JSON Lines in an App Group container | ADR 0002 |
| Crypto | CryptoKit; Secure Enclave P-256 | Copied in from `BeforeKit` — see below |
| Anchoring | OpenTimestamps, submitted to **all three** calendars, not first-success-wins | Copied in from `BeforeKit`. The calendars are a real operational dependency — ADR 0004 |
| Tests | Swift Testing (`import Testing`, `@Test`, `#expect`) | |
| Sync | None in v1. CloudKit `CKSyncEngine` when triggered | §7 |
| Chain | None in v1 | ADR 0001, ADR 0004 |

Third-party dependencies in v1: **none**. This is a target, not an accident. The
one that would be justified is GRDB, and §6 states the measured trigger that
would justify it.

### Reuse from the existing app — by copying, never by reference

The proven code lives in another repository (`before`, `Sources/BeforeKit/`).
**The consumption mechanism is: copy the source files in.** Not an SPM path
dependency, not a git submodule, not a symlink.

`Seal.swift` and `Calendar.swift` are together roughly 250 lines. They are
copied into `Sources/CompassInfrastructure/`, with a header comment naming the
origin repository, the file, and the date copied. After that, `compass` builds
with no reference to any path outside itself.

This is decided rather than left open because the alternative is worse in a
specific, checkable way. A `.package(path: "../before")` makes Compass
unbuildable the moment that folder moves, and the folder in question sits in a
downloads directory alongside dozens of other repositories — a directory that
gets cleaned. Neither repository protects the other. A build that breaks because
an unrelated folder was tidied is exactly the kind of wall that historically
triggers a fork under a new name. Copying also makes the "third-party
dependencies in v1: none" line above true by construction rather than true by
exception.

What is worth copying:

- `Signer` — Secure Enclave with an honest software fallback.
- `Calendars.anchor(_:)` — OpenTimestamps submission.
- More important than either, the hand-written canonical-bytes discipline in
  `Entry.sealBytes`, whose stated reason applies unchanged here: key order is not
  a promise Swift makes across releases.

Three things must be **fixed while copying**, not copied verbatim:

1. Do **not** copy `actor Log`'s `persist()` at all. It re-encodes and rewrites
   the whole array on every append, which is correct for one entry a day and
   wrong for a tap-driven tracker. See §6.
2. `Signer.sign` computes `SHA256(text)` and hands the resulting `Data` to
   CryptoKit, which hashes again — so it signs `SHA256(SHA256(text))`. The
   original app verifies the same way, so it is self-consistent and correct, but
   Compass promises an external verifier. **Compass MUST NOT call
   `Signer.sign(_ text:)` on the achievement path.** The convention Compass uses
   is fixed in `docs/achievement-protocol.md` §6.7.
3. `Signer` as written **cannot restore a Secure Enclave key across app
   launches.** Its only two initialisers mint a fresh enclave key or restore a
   software key; there is no `init(enclaveKeyData:)` and `exportableKey` returns
   nil for enclave keys. Copied verbatim, every launch produces a different
   public key, achievements signed in different sessions carry different
   signers, and the "this came from one device" claim collapses. The fix is
   specified in §8 and recorded in `memory/known-bugs.md`.

## 2. Module structure

Four targets in one package. Swift enforces `import` at target granularity, so a
target that does not declare a dependency physically cannot import it — the
compiler is the boundary guard, without four `Package.swift` files.

```
compass/
  Package.swift
  Sources/
    CompassDomain/          imports: Foundation only
    CompassApplication/     imports: CompassDomain
    CompassInfrastructure/  imports: CompassDomain
      Composition.swift     the composition root — the only place infrastructure
                            is constructed
    CompassUI/              imports: CompassApplication, CompassDomain
  Tests/
    CompassDomainTests/     ~80% of all tests. Pure. Milliseconds.
    CompassApplicationTests/
    CompassInfrastructureTests/
  App/                      thin shell: calls the composition root, nothing else
  Widget/
  project.yml
```

**Infrastructure is still constructed in exactly one place. That place is now
inside the package.** The rule did not change; only its location did. The
composition root was `App/CompassApp.compose()` until 2026-07-31, and `App/` is
not compiled by `swift test` and has no test target — so every line of wiring
sat where no test could reach it. Mutation proved the cost rather than asserting
it: restoring a `preconditionFailure` on the store-open failure path, and
separately deleting the argument that hands the journal its already-known
high-water mark, each left the whole suite green. Both lines were fixes for real
bugs, and either could have been deleted in silence.

So the wiring moved to `CompassInfrastructure/Composition.swift`, which the test
suite compiles, and `App/` became a shell holding no branch, no `catch` and no
forwarded argument — because an argument in `App/` is an argument no test can
see. It is not in `CompassApplication` for a mechanical reason: `CompassUI`
imports `CompassApplication`, so composing the app there would require the
import to run backwards. `memory/decisions.md`, 2026-07-31.

Only one boundary is load-bearing: **Domain must not know Infrastructure
exists.** Application-versus-Domain is a nicety. If adding one field starts
requiring coordinated edits in four targets, collapse `CompassApplication` into
`CompassDomain`. The diagram is not the deliverable; the daily additive change
being cheap is the deliverable.

### Ports, all declared in Domain, all `Sendable`

```swift
protocol EventSink   { func append(_ event: Event) async throws }
protocol EventSource { func replay() async throws -> [Event] }
protocol Clock       { func now() -> Date; func today(cutoffHour: Int) -> Day }
protocol Attestor    { func attest(_ claim: AchievementClaim) async throws -> Attestation }
```

`Attestor` is the anti-rewrite hinge. `OpenTimestampsAttestor` ships first.
`SoulboundAttestor` arrives later behind the identical protocol. An achievement
holds a list of attestations, so old records carry one and new records carry
two, and nothing migrates.

## 3. Data model

### `Day` — the highest-value type decision in the project

```swift
struct Day: Hashable, Comparable, Codable, Sendable {
    let ordinal: Int   // days since 2000-01-01, proleptic Gregorian, civil
}
```

`Day` is **not** a `Date`. It has no instant, no timezone and no locale. Streak
arithmetic is integer arithmetic on labels, so DST, leap seconds, and flying
between timezones cannot corrupt it.

**Encoded as the ISO string `"2026-07-31"`, never as the ordinal.** The internal
integer is for arithmetic; the on-disk form is for a human reading the log with
`grep`, which is a large part of why the log is text at all.

Only `CompassInfrastructure`'s `SystemClock` converts `Date` to `Day`, applying
a **04:00 day boundary**. A check-in at 01:30 counts for the previous day. One
constant in Domain, zero UI, and it removes the single most common "I did it but
the app says I didn't" moment.

### Events — the only truth

Nine kinds, closed set, but encoded as a `RawRepresentable` string wrapper
rather than an enum, so an unknown kind from a newer build decodes cleanly
instead of crashing.

```
habitCreated(habitID, name)
habitRenamed(habitID, name)                       cosmetic; never affects the fold
habitArchived(habitID, on: Day)
habitUnarchived(habitID, on: Day)
checkedIn(habitID, day: Day, source)              source: tap | widget | shortcut
checkInRevoked(habitID, day: Day)                 compensating event, never a delete
achievementAwarded(achievementID, …)              see §5 and the protocol document
achievementRevoked(achievementID, reason)
subjectNamed(name)                                optional, self-declared, unverified
```

**`subjectNamed` was added on 2026-07-31, additively, by exactly the mechanism
this section describes** — a new `kind` string, reusing `name`, a payload key
this document had already frozen. It is the optional self-declared name for the
person the record is about; `docs/open-questions.md` records the question and
`memory/decisions.md` the choice. It is listed here rather than left implicit
because the per-kind payload table below is the specification week 1b's
canonical encoder is written from, and a kind missing from that table at the
moment the format freezes is the same class of omission as the `payload` gap
this section documents further down.

**Kinds deliberately removed, and why removing them is free.** Earlier drafts
reserved `habitCadenceChanged(habitID, cadence, effectiveFrom: Day)`,
`dayNoteAttached(habitID?, day: Day, text)`, and a `cadence` payload on
`habitCreated`. Schedules and notes are both named non-goals in
`docs/product.md`, so reserving them was keeping a banned feature alive in the
data model and dragging its consequences in with it — a cadence field implies
settings UI to drive it, and a non-scheduled day is neither done nor missed,
which is what the deferred third `DayStatus` case exists for.

`EventKind` is a `RawRepresentable` string precisely so a kind can be added
later without a format change. That is the stated reason it is a string. So
reserving these costs nothing to give up: if schedules are ever genuinely
wanted, the non-goal is overturned in writing in `memory/decisions.md` and the
kind is added additively that day. See `docs/product.md` — non-goals are the
authority over this document.

`source` on `checkedIn` has three values in v1, not four. `backfill` is
deliberately absent because no backfill surface ships in v1 — see §10. The
`facts` partition in `docs/achievement-protocol.md` §3.4 still carries
`source_live` and `source_backfill`, because those are inside the digest and
cannot be added later; in v1 `source_backfill` is always `0`.

Every event record carries, from the very first write:

```
v            always 1, never bumped — see §8
id           UUID, for cross-device dedupe
device       writer identifier — see below. NOT a hardware identifier.
lamport      per-writer monotonic counter
kind         string
day          Day, the civil day this is ABOUT
recordedAt   the instant the user tapped — metadata, never read by the fold
zoneOffset   device UTC offset in minutes at record time
source       for checkedIn
prev         content_hash of the previous event on THIS writer's chain, or 32
             zero bytes for the first event on a chain
extra        forward-compatibility bag, round-tripped losslessly
```

`device`, `lamport` and `prev` exist from day one even though there is one
device and no sync. They cost nothing now and they cannot be retrofitted later
without invalidating every hash computed before the change. This is the one
irreversible early decision in the project — with the single escape hatch stated
in §11, which closes permanently the first time anything is signed.

#### `content_hash` — defined here because the rest of the corpus depends on it

`prev` chains events together and `docs/achievement-protocol.md` §4 builds the
`evidenceRoot` Merkle tree out of per-event hashes. Both need the same
quantity and it must be named once, here, before any code:

```
content_hash = SHA-256(event canonical bytes)
```

The event canonical bytes are hand-written, UTF-8, no whitespace, in **exactly
this key order**, using the same escaping rules as
`docs/achievement-protocol.md` §6.3:

```
{"v":1,"id":<string>,"device":<string>,"lamport":<int>,"kind":<string>,
 "day":<string>,"recordedAt":<int>,"zoneOffset":<int>,"source":<string>?,
 "payload":<object>,"prev":<base64>}
```

**`payload` carries the kind-specific fields, and it is REQUIRED.** Always
present, never omitted, never `null` — a kind with no fields of its own emits
`"payload":{}`. Keys are written in exactly the order listed here, per kind, no
whitespace:

```
habitCreated       {"habitID":<string>,"name":<string>}
habitRenamed       {"habitID":<string>,"name":<string>}
habitArchived      {"habitID":<string>}
habitUnarchived    {"habitID":<string>}
checkedIn          {"habitID":<string>}
checkInRevoked     {"habitID":<string>}
achievementAwarded {"achievementID":<string>}
achievementRevoked {"achievementID":<string>,"reason":<string>}
subjectNamed       {"name":<string>}
```

`day` and `source` stay at the top level rather than moving inside `payload`.
They are already digested where they are, and moving them would be a format
change that buys nothing. `source` is operational metadata, not semantics.

**`payload` is a closed structure, not a second `extra`.** In v1 every key
inside it has a frozen meaning and a frozen position, and **an unknown payload
key makes the event invalid** — it is not ignored, not round-tripped, not
tolerated. This is the one place where the corpus's usual
forward-compatibility instinct is wrong: silently accepting a semantic field
you cannot hash is precisely the failure `payload` was added to close. New
semantics arrive as a new `kind`, never as a new key in an existing payload.
Contrast `extra`, which stays open and stays undigested, and therefore must
never carry anything that has to be provable.

**Forward compatibility for evidence attachments.** Attaching a photo or a voice
note to a check-in is not a v1 feature and is not scheduled. This note exists
only so that adding it later is additive rather than a format change, since the
canonical form cannot be revised after the first signature:

- Evidence is **optional**. The absence of evidence must never invalidate a
  normal check-in, and a check-in must never require it. The default gesture
  stays one tap.
- Evidence lives in its own top-level object, **not** inside `payload` and
  **not** inside the envelope — so adding it does not disturb any existing
  digested field or its ordering. The reason is not layout, it is meaning:
  **`payload` is what happened; evidence is what was available to observe it.**
  A check-in is a claim by the user, and it is complete on its own. An
  attachment is a witness to that claim, and a witness is never what makes the
  claim true.
- Media is **referenced by content hash, never embedded.** The event commits to
  `sha256(file)`; the bytes live outside the log. An event proves the evidence
  existed at that point in history, and the hash proves the file has not changed
  since. Media never enters the canonical bytes, never enters the chain, and
  never reaches an anchor.

Recording this costs nothing now and prevents Phase 2 from becoming a migration.
It is not a commitment to build the feature; see `docs/product.md`.

Hashing `name` is safe and deliberate: a hash does not reveal it. This does not
weaken `docs/achievement-protocol.md` §3.4, which keeps habit *names* out of the
achievement `facts` because those are published in cleartext. A digest is not a
disclosure.

**Why `payload` exists — recorded 2026-07-31, before any code was written.**
The first version of this section omitted it. Every field saying *which habit an
event is about* was therefore outside the digest, so editing `habitID` on any
line left its `content_hash` unchanged, left the `prev` chain intact, and left
`docs/achievement-protocol.md` §4's `evidenceRoot` verifying. A hundred-day
meditation streak could have been rewritten into a hundred-day reading streak
with every proof still checking out, Bitcoin anchor included. The guarantee this
entire corpus rests on — that a sealed record cannot be restated afterwards —
did not hold.

It was correctable only because nothing had been signed; §11's escape hatch
closes permanently at the first signature. It is written down rather than
quietly patched so that the next person tempted to trim the canonical form can
see what trimming it cost the first time.

Rules, all of which are frozen at the first write:

- `recordedAt` is an integer count of milliseconds since the Unix epoch. There
  is no floating point anywhere in a digested value.
- Optional fields that are absent are **omitted entirely**, never emitted as
  `null`. In v1 only `source` is optional.
- **`prev` participates.** That is what makes the chain a chain: altering any
  earlier event changes that event's `content_hash` and therefore every later
  one. This holds only for fields inside the canonical form — which, since
  `payload` was added above, is now every field that changes what an event
  means. Before that fix the sentence was false in exactly the way that
  mattered.
- **`extra` does not participate**, for the same reason it is excluded from the
  achievement digest in the protocol document: an old build cannot hash fields
  it has never seen. The consequence is identical and must be understood —
  anything that has to be provable goes in a named field, never in `extra`.
- `content_hash` is **recomputed on read, never stored on the line.** Storing it
  would put a value on disk that can disagree with the bytes next to it, and the
  only honest response to that disagreement is to recompute anyway.

The on-disk JSON line is not required to be byte-identical to the canonical
form — it carries `extra` and may order keys differently. Canonical bytes are
derived from the decoded event, and the encoding-stability test in §9 is what
pins them.

#### `device` — a random UUID, and nothing else, ever

`device` is signed, anchored, and present inside every exported achievement
handed to a stranger, via `witness.logHeads`. So it is specified rather than
left to whatever is convenient at the keyboard:

- `device` is a **randomly generated 128-bit UUID**, created on first launch and
  stored locally.
- It MUST NOT be `identifierForVendor`, a keychain-persisted hardware-adjacent
  value, an Apple ID, the device name, or anything derived from any of those.
  "Farros's iPhone" inside a signed record handed to a recruiter is the failure
  being designed out.
- It is never displayed anywhere in the UI.

`docs/adr/0004` bans device identifiers from the chain as "a fact about a
person's day". The same value ships inside the record people actually receive,
so it gets the same protection. Recorded as an architecture rule in
`.claude/skills/architecture.md` so a future session cannot substitute
something convenient.

**"Device" means writer, not phone.** The app process and the widget process on
one phone are two writers with two `device` UUIDs and two chains. See §4.

**Total order is `(lamport, device)`. Never wall-clock.** Clocks move backwards
— NTP corrections, manual changes — and `recordedAt` is therefore not a safe
sort key. Lamport first so causality holds, device as a deterministic
lexicographic tiebreak so two devices compute identical results.

**Nothing is ever mutated or deleted.** Un-checking appends a
`checkInRevoked`; the fold resolves the `(habit, day)` cell last-writer-wins
under the total order.

### Projection

```swift
func project(_ events: [Event]) -> Projection
```

Pure and total. No clock, no `Calendar.current`, no `TimeZone.current`, no
locale, no I/O, no floating point. Every accumulator keyed by `habitID`; there
are no global accumulators. That last rule is not stylistic — a globally
order-dependent accumulator is the exact bug that destroyed replay determinism
in this user's prior event-sourced work, and it is mechanically forbidden by the
shard-invariance test in §9.

`DayStatus` is `{ done, missed }` in v1. A third case, `neutral`, is designed
for and deferred — see §10.

## 4. Event flow — the tap path

This is the whole design.

```swift
// TodayModel, @MainActor
func toggle(_ habit: Habit) {
    let event = Event(kind: .checkedIn, habit: habit.id,
                      day: clock.today(cutoffHour: 4), at: clock.now())

    projection.apply(event)          // 1. state changes NOW, synchronously
    haptics.impact(.soft)            // 2. finger feels it NOW
    journal.appendSync(event)        // 3. durable NOW — one write(2), ~120 bytes

    Task { await log.absorb(event) }               // 4. actor catches up
    Task { await achievements.evaluate(projection) } // 5. may raise a certificate
}
```

Lines 1 to 3 are synchronous. **There is no `await` between the tap and the
pixel, and none between the tap and durability.** `journal` is a `final class`
guarding an open `FileHandle` with `Synchronization.Mutex`, called from the main
actor. Appending ~120 bytes to an open descriptor is microseconds, comfortably
inside a frame. Kill the app 10ms after the tap and the check-in survives.

The cheap fallback if the synchronous journal proves annoying is to delete line
3 and rely on line 4; the loss window is sub-millisecond in practice. It is kept
because "did my tap actually save?" is precisely the doubt that erodes trust in
a daily driver, and this removes it by construction rather than by hope.

### Launch path

The first frame must render correct data with **zero awaits**. Do not
`await log.replay()` before showing anything.

A small `TodaySnapshot` (habit names, today's booleans, the totals) is written
on every change and read **synchronously** in `TodayModel.init`. The full log
replays in a `.task` immediately afterwards and reconciles. If the snapshot and
the replay disagree, **the replay wins** and the snapshot is rewritten. The log
is the source of truth; the snapshot is a disposable cache and may be deleted at
any moment.

### Concurrency boundaries — four in-process, plus one across processes

1. `@MainActor` — `TodayModel` and all UI. `@Observable final class`, **not** an
   actor. Observation and actors do not compose: you cannot synchronously
   observe state across an actor hop, and any `await` introduced here lands
   directly in the tap path.
2. `actor EventLog` — owns the file and the in-memory event array. Serial by
   construction, so no locks.
3. `nonisolated` pure functions — projection, streak, achievement evaluation.
4. `struct Attestor: Sendable` — networking is **not** an actor. `URLSession` is
   already concurrency-safe; wrapping it only serialises calls that need not be.

### The fifth boundary: two processes write `events.jsonl`

`Synchronization.Mutex` is an in-process lock. It does not span processes. From
week 2 the interactive widget appends to the same file from a second process,
and nothing above coordinates that. This must be specified **before the widget
ships**, not discovered afterwards, because the failure is silent: every test in
§9 uses synthesised in-process event streams and would pass while real data
corrupts.

Two independent things can break, and they need two different answers.

**1. The chain must not fork.** `lamport` is a per-writer counter and `prev` is
the previous event on that writer's chain. Two processes incrementing one
counter produce duplicate `(lamport, device)` pairs, so the total order stops
being total; two processes each computing `prev` from their own in-memory view
fork the hash chain, and `witness.logHeads` — one head per writer — stops having
a well-defined value.

**The answer is a separate writer identity per process.** The app has one
`device` UUID, the widget extension has another, each generated on that
process's first write and stored in the App Group. Each maintains its own
`lamport` sequence and its own `prev` chain. `logHeads` then carries two heads
for one phone, which is exactly what the field is shaped for.

This is not a workaround, it is the design already chosen: ADR 0002 rejects a
single global hash chain precisely because concurrent appenders fork it, and
adopts per-writer chains with the anchor covering the sorted set of heads. Two
processes on one phone are the first instance of that case, arriving in week 2
rather than at the second device.

**2. A line must not tear.** Both writers append to one file, so a partially
written line from one process can land in the middle of another's.

- Every event is written as **one `write(2)` of one complete line including its
  trailing newline**, to a descriptor opened `O_APPEND`. At ~120 bytes this is a
  single atomic append; there is no seek-then-write sequence to interleave.
- Any operation that must **read the tail and then append** — recovering
  `lamport` and `prev` after a cold start of either process — takes an advisory
  `flock` on the file for the duration of the read-then-write. This is the only
  place a cross-process lock is taken, and it is never taken on the tap path
  after the first write of a process's lifetime.
- The widget never rewrites, compacts, or truncates. Only the app process does,
  and only under the same lock.

**Test it, per §9.10.** Spawn two writers against one file, interleave several
thousand appends, then assert: every line parses, no `(lamport, device)` pair
appears twice, and each writer's chain verifies unbroken from its first event to
its head. A design decision about concurrency with no adversarial test behind it
is a hope.

## 5. Achievements

Full field-level specification is in `docs/achievement-protocol.md`. The
architectural points that belong here:

**Rules are data, evaluators are code.** A rule is a `RuleSpec` value shipped as
JSON in the bundle. Each `RuleKind` has a small Swift evaluator. Adding an
achievement is a JSON row, not a code change, and the engine backfills it over
existing history with `earnedOn` correctly set to the historical day. Hard-coded
`if streak == 100` rules require a version-gated backfill migration per
achievement, which is the migration pain this project cannot afford.

**v1 ships two evaluator kinds only: `streak` and `total`.** Four more
(`rate_in_window`, `first_ever`, `distinct_weekdays`, `all_of`) are named in the
protocol so the format does not change when they arrive, and are not
implemented. An unknown `RuleKind` is skipped with a warning and the rule is
preserved on disk; an older build never destroys rules it does not understand.

**The engine is a pure, idempotent, re-runnable function.** Same inputs, bit
identical outputs. Achievement IDs are deterministic (`"<ruleID>@<earnedOn>"`),
so replaying the entire log an unlimited number of times produces the identical
award set. This is what makes retroactive edits and rule backfill tractable at
all.

**An earned achievement is then recorded as a fact, not left as a derivation.**
The engine computes eligibility; a separate guarded step appends
`achievementAwarded` exactly once. This matters because the award gates an
irreversible external side effect: if a rule is later reworded, a purely derived
award would silently un-award something already anchored to Bitcoin. Each
achievement therefore carries a **frozen copy** of the rule that fired, so
changing or deleting that rule later has no effect on records already earned.

**Rule set, tuned to roughly a dozen awards a year:** per habit at 7, 30, 100,
365 and 1000 consecutive days; plus all-habit totals at 100, 500 and 1000 days.
Rarity is deliberately absent — see §10.

**Habit names are never inside a digest.** `facts` carries the opaque `HabitID`,
never the human-readable name. The name lives in a mutable local file and is
resolved at render time, exactly as §5.2 of the protocol already does for
titles. The reason is that the achievement record is the artifact designed to be
handed to a stranger, and it is immutable, signed and anchored — so a name
written into it can never be taken back. A user who names a habit after a
recovery programme, a medical routine or a therapy task, earns a certificate,
and later regrets the name would otherwise have no remedy at all, forever. See
`docs/achievement-protocol.md` §3.4.

**The 72-hour provisional window.** An achievement is signed locally and shown
to the user immediately, but is not submitted for public anchoring until 72
hours have passed. The window costs one timestamp comparison in a background job
and it removes an entire reversal UI from v1.

If the user un-checks a day the achievement depended on **within** that window,
nothing was ever published, so nothing needs reversing on the outside — but the
record is still **not deleted**. A `Revocation` is appended to `awards.jsonl`
like every other state change and the projection filters the achievement out of
the certificate list. `awards.jsonl` is strictly append-only; a documented
deletion path inside it would be implemented as a whole-file rewrite, which is
the operation ADR 0002 disqualifies on flash-write grounds and the one most
likely to lose the file on a crash. Invariant 4 in the protocol —
"never mutated and never deleted" — then holds with no exception.

If it happens **after** submission, the same appended `Revocation` is what the
certificate list renders as a revoked entry, reading that the user edited a day
it depended on. **You never erase a published entry; you post a reversal.**

The difference between the two cases is therefore what the outside world saw,
not whether the local record survives. Both append.

## 6. Storage

Append-only JSON Lines, one event per line, in an **App Group container from the
first commit**.

```
Group/
  events.jsonl        append-only, per-device hash-chained — the only truth
  awards.jsonl        append-only: achievement and revocation records
  attestations.jsonl  append-only, last-write-wins per achievement ID
  rules/*.json        bundle + user directory, hot-reloadable
  snapshot.json       cache. Deletable. Never the source of anything.
```

Attestations live in their own file **because they mutate while achievements do
not**. Separating mutable from immutable is what lets `awards.jsonl` be strictly
append-only.

### What is actually irreplaceable — three tiers, not two

An earlier form of this rule said `events.jsonl` is the only file that is not
rebuildable and everything else may be deleted and recomputed. That is wrong,
and wrong in the dangerous direction: it licenses deleting the least protected
files in the project.

| Tier | Files | Why |
|---|---|---|
| **Irreplaceable** | `events.jsonl`, `awards.jsonl` | Events are the only truth. Awards are recorded as *facts* with a frozen rule copy, precisely so recomputation under changed rules cannot un-award something already published — so recomputing them is not the same operation as reading them. |
| **Irreplaceable in part** | `attestations.jsonl` | `otsProof`, `signature`, `publicKey` and `chain` are **not** recomputable. Re-submitting a deleted OTS proof yields a strictly later Bitcoin timestamp, which destroys the "it is not backdated" property that ADR 0004 calls the entire argument for the pairing. The signature is unrecomputable once the enclave key is gone. `ChainRecord` is the sole record that makes ADR 0001's chain-death insurance work. Only `state` and the timestamps in this file are recomputable. |
| **Disposable** | `snapshot.json`, projections, any derived table | Delete freely. A projection bug is never data loss and a change to how anything is computed costs zero migration. |

The two consequences worth keeping from the old wording still hold for the
disposable tier, which is where they were always true. The mirror of this table
is in `.claude/skills/architecture.md`.

### App Group — the real constraint, stated as what it is

Earlier drafts said the App Group is required from the first commit and that
retrofitting it is a rewrite. That is overclaimed, and the overclaim was
load-bearing in the wrong direction: App Groups need an entitlement, which needs
a provisioning profile, which needs the paid developer account — so one
overstated sentence turned a purchase into a hard gate on all storage code, for
a project whose documented failure mode is that day one is where projects die.

The container is a directory URL. `architecture.md` already requires that
infrastructure be constructed in exactly one file, the composition root in
`CompassInfrastructure/Composition.swift`. The honest statement of the
requirement is therefore:

> **Every path must obtain its base URL from a single injected `storeURL`.** No
> file path is constructed anywhere else. Switching that URL from
> `.documentDirectory` to
> `FileManager.containerURL(forSecurityApplicationGroupIdentifier:)` is then one
> line plus a file move, and it MUST happen before the widget ships in week 2.

That preserves the real constraint — the widget cannot read a container it has
no access to — and removes a false dependency on the developer account from the
first line of code.

### File Data Protection, and the iCloud backup position

Both are stated because otherwise a default silently applies, and the default is
a decision nobody made.

`events.jsonl` is a plaintext, greppable behavioural diary — greppability is a
deliberate feature, per ADR 0002 — and from week 2 a Home Screen widget must
read it while the device is locked. That rules out `NSFileProtectionComplete`.

**Decision:** the App Group container is set to
`NSFileProtectionCompleteUntilFirstUserAuthentication`. This is the strongest
class compatible with a widget that renders on a locked screen. State the
consequence rather than hiding it: **after the first unlock following a reboot,
anyone holding the unlocked phone, and any forensic extraction of it, gets the
whole diary in plain text.** ADR 0004 refuses to publish a behavioural diary on
a chain; it would be incoherent to leave the identical diary undefended on disk
and never say so.

**Decision:** iCloud device backup is **deliberately included**, not inherited.
`isExcludedFromBackup` is NOT set on the container. Until CloudKit sync exists,
device backup is the only thing standing between a dropped phone and total loss
— see §8. The cost is that the plaintext diary is uploaded to Apple, so the
framing in `docs/product.md` and `README.md` says "no server of ours and nothing
to sign in to" rather than implying nothing ever leaves the phone.

### When the log is damaged

§9.6 truncates the file at every byte offset, which covers a crash mid-append
and nothing else. A torn interleaved write, a corrupted middle line, or a `prev`
mismatch has no specified behaviour — and with `events.jsonl` declared the only
truth, the plausible implementations range from "the user cannot open their
habit tracker" to "the streak silently shortens and nobody notices". Both are
restart triggers.

**The policy, in this order:**

1. Copy the file to `events.jsonl.damaged-<timestamp>` **before touching
   anything**. Never rewrite the original in place.
2. Replay the longest valid prefix — every line that parses, in order, up to the
   first line that fails to parse or whose `prev` does not match the computed
   `content_hash` of its predecessor on that writer's chain.
3. Continue past the break only for lines belonging to a *different* writer's
   chain, since per-writer chains fail independently.
4. Surface **one** notice, once, saying how many days were recovered and where
   the damaged copy is. Not on the launch path, and never again after it is
   dismissed.
5. Never silently drop lines and never refuse to launch.

A test injects a corrupted middle line and a forked chain and asserts each step.
See §9.11.

### Why not SQLite, and the measured trigger that would change it

Measured on this machine, for a 5-year × 5-habit log (10,493 events, 1.9 MB):
full projection rebuild from zero **193 ms**; hash-chaining every event **60
ms**; and the whole-array rewrite pattern used in the existing Shipped app
**145 ms and a 1.9 MB flash write per checkbox tap**. At 10 years × 10 habits
(41,975 events) those become 865 ms, 261 ms, and 644 ms / 7.7 MB per tap.

The measurement kills whole-file rewriting, not JSON Lines. Appending one line
to an open descriptor is O(1) and does not appear in that table. What the table
does say is that a full rebuild is not free, which is why the launch path reads
a snapshot and replays afterwards rather than replaying first.

**Trigger to revisit:** a test asserting full replay on the reference device
fails a 250 ms budget, or a feature genuinely needs a query rather than a fold.
The fix in that order is (a) a snapshot with compaction, still a cache, still no
migration; then (b) GRDB, chosen over SwiftData and SQLite.swift for the reasons
in ADR 0002. Do not build either before the assertion fails.

**Log compaction:** deferred. Trigger: the log exceeds roughly 50,000 lines or
the replay budget above fails. Compaction folds revoked check-ins into their
outcome and rewrites the file; it is a cache-shaped operation and must preserve
the hash chain, which is the part that makes it non-trivial and the reason not
to do it early.

## 7. Sync

**Not in v1. There is one device.**

What v1 does pay for is the *shape*: `device`, `lamport` and `prev` on every
event, per-device hash chains rather than one global chain, and a total order
that does not use wall-clock time. Those fields are frozen into the canonical
encoding, so they cannot be added later without invalidating every hash. They
cost nothing today.

When sync happens it is **CloudKit `CKSyncEngine` against the private
database**, and the merge is a set union, because events are immutable and
uniquely identified. A grow-only set is a CRDT — the simplest one there is — so
choosing immutability buys CRDT semantics without importing a CRDT library. The
only genuine conflict is `checkedIn` versus `checkInRevoked` for the same
`(habit, day)` on two offline devices, and the fold resolves that cell
last-writer-wins under the total order, identically on every device. The system
is exactly two CRDTs, a G-Set of events and an LWW-Register per cell, and
neither needs a dependency.

**Trigger:** a second device exists and is actually used — an iPad, a second
phone, or a watch. Not "might one day".

**Hard invariant when it arrives:** the habit UI never awaits a network call.
Sync failing permanently must be invisible on the main screen. Test the
signed-out-of-iCloud path before trusting any of it.

**Also required before trusting sync:** a shuffle-invariance test asserting that
permuted arrival order produces an identical projection. Without it, two devices
will diverge silently and surface months later as a phantom or missing
achievement.

## 8. Auth and identity

**There is no auth in v1.** No account, no sign-in, no user record. One person,
one phone, one file. Adding an identity system would be adding the hardest part
of a multi-user product to a single-user app.

The only key in v1 is the **Secure Enclave P-256 signing key**, created on first
launch, non-extractable, used to sign achievement digests. It is never shown,
never named, never exported, and the user is never told it exists. On the
simulator there is no enclave and the key falls back to software; the record
says so, rather than letting a simulator-made proof look as strong as a
phone-made one.

### The key must survive relaunch, and the copied code does not do that

"Created on first launch" is a promise the inherited `Signer` cannot keep. Its
`init(preferEnclave:)` unconditionally calls
`SecureEnclave.P256.Signing.PrivateKey()`, minting a brand-new key on **every
construction**, and there is no initialiser that restores one. So without this
fix, every launch signs with a different public key and "these achievements came
from one device" is false.

Required when the `Signer` copy is made, before the first achievement is signed:

- On first launch, persist the enclave key's `dataRepresentation` to the keychain
  with `kSecAttrAccessibleAfterFirstUnlockThisDeviceOnly` — after first unlock,
  because the widget process must be able to construct the signer, and
  this-device-only because a key that syncs is not a device attestation.
- Add `init(enclaveKeyData:)` restoring via
  `SecureEnclave.P256.Signing.PrivateKey(dataRepresentation:)`.
- A test asserts that two successive `Signer` constructions in one process, and
  two across a simulated relaunch, yield the **same** `publicKey`. See §9.12.

### Export is a bundle, not a log dump

This is the single artifact the whole survival story rests on, so it is defined
here in the same words as `docs/product.md`, `memory/next-tasks.md` and ADR
0002, and the four copies must not drift.

An earlier form of this document said achievements and proofs survive device
replacement "because the record and the OTS proof are in the exported bundle",
while export was defined everywhere else as "newline-delimited canonical JSON of
the whole log" — that is, `events.jsonl` alone. Achievement records live in
`awards.jsonl` and OTS proofs live in `attestations.jsonl`. Neither was in the
export. A user who followed the documents exactly, exported weekly, and then
dropped their phone in a river lost every signature and every Bitcoin proof.

**`export` produces a directory or zip containing:**

```
events.jsonl              the whole log, canonical JSON, one event per line
awards.jsonl              every achievement and revocation record
attestations.jsonl        signatures, OTS proofs, anchor state, chain records
rules/*.json              the rule JSON frozen into each award
habits.json               HabitID -> display name, so a name can be revealed
publickey.pem             the P-256 public key(s), including rotated ones
proofs/*.ots              every OTS proof file, upgraded where available
salts.json                per-token commitment salts, if any token was minted
manifest.json             per-file SHA-256 digests, plus the export timestamp
```

**A test asserts that a fresh install fed only the exported bundle reproduces
every achievement bit-identically and verifies every proof.** An unexercised
escape hatch is not an escape hatch. See §9.13.

### What happens when the phone dies before CloudKit exists

Named here because it is the largest data-loss vector in the design and no
document previously listed it as a risk. There is no server, sync is deferred
until a second device exists, and the entire record lives as one set of files in
one container on one phone. Phone lost, stolen, bricked or wiped in week three
means the streak, every achievement and every anchor are gone permanently.

Three mitigations, all cheap, none requiring a server:

1. **iCloud device backup is deliberately enabled** for the container — see §6.
   It is the de facto backup and it is stated rather than inherited.
2. **A scheduled `BGProcessingTask` writes the full export bundle to the user's
   iCloud Drive** on a fixed cadence. This is the user's own iCloud, with no
   operator, which is the same basis on which CloudKit is permitted by the
   non-goals in `docs/product.md`.
3. **A first-launch check** that the last successful export is under N days old,
   surfacing once — not on the launch path and never nagging — if it is not.

Recorded as a named hazard with its mitigation in `memory/known-bugs.md`.

### Device replacement, and what a stranger can conclude across it

Known limit, inherited from the existing app: **the enclave key does not survive
device replacement.** Achievements and proofs survive, because they are in the
exported bundle. The ability to extend that particular key's chain does not.

The gap that was not previously stated: nothing links the old key to the new
one. By the time a new phone exists the old key is unreachable, so it cannot
sign its successor. A stranger handed a bundle spanning a device replacement
sees achievements signed by two unrelated public keys and must simply *trust*
that they belong to the same person — which is exactly the trust the mission
sentence promises to eliminate. The user never learns this, because the user is
never told the key exists.

**Required, in this order:**

- During normal operation, the current key periodically signs a **forward-looking
  rotation authorisation** — a short record authorising a successor public key
  presented alongside the bundle — refreshed on a fixed cadence. This is the only
  mechanism that can authorise a successor *before* the phone is lost, so it is
  the one that has to exist first.
- On first launch of a new device, if a prior public key is present in the
  imported bundle, append a `keyRotated` event carrying the new public key, and
  anchor its introduction via OTS so at minimum the **ordering** of the two keys
  is provable.
- ADR 0004's verification procedure states plainly what a verifier can and cannot
  conclude across a rotation: with a valid authorisation, continuity is proven;
  with only a `keyRotated` event and an anchor, the ordering is proven and the
  continuity is asserted, not proven.

Re-keying is recorded as an additive event, never as a reason to reset history.

Blockchain identity — passkeys, smart accounts, owner sets, recovery keys — is
specified in ADR 0003 and is not part of v1. The single sentence that matters if
it is ever built: **because achievements are soulbound they cannot be moved, so
the address must be permanent and the signing authority must be replaceable,
which rules out a plain EOA.**

## 9. Testing

Worth writing, all pure, all in `CompassDomainTests`, all against an injected
fake clock, all running in milliseconds:

1. **Day and streak arithmetic, exhaustively.** 23:59 and 00:30 check-ins; the
   04:00 cutoff; DST in both directions; travel Surabaya to anywhere and back;
   leap day; double-toggling one day; a gap of exactly one day. This is where
   the real bugs live, and a wrong answer here is what makes the user stop
   trusting the app, which is what makes him rebuild it.
2. **Replay parity.** Replay the log twice; assert byte-identical serialised
   state.
3. **Shard invariance.** Split the log by `habitID`, fold each shard
   independently, merge, and assert the result equals folding the whole. This
   mechanically forbids the global-accumulator bug rather than trusting review
   to catch it. Highest-value single test in the project.
4. **Incremental equals full replay.** After a random event sequence,
   incrementally-applied state must equal a from-zero rebuild.
5. **Achievements fire exactly once, ever**, under full replay, after a crash,
   and after a reinstall from the log.
6. **Journal crash-safety, properly.** Write a log, truncate the file at *every*
   byte offset, and assert it still opens with all complete lines intact and the
   partial tail dropped. This is what makes the synchronous-append design honest
   rather than decorative.
7. **Canonical encoding stability.** Assert the digest of a fixed achievement
   equals a hardcoded hex string. If this test ever needs updating, something
   irreversible has happened.
8. **Attestation failure leaves the achievement earned and pending, and retries
   on *both* paths.** Assert the pending queue drains when a
   `BGProcessingTask` fires, **and** that it drains opportunistically on next
   launch. Both, not either — this document previously said "on next launch"
   while `.claude/skills/ios.md` and `memory/next-tasks.md` said
   "`BGProcessingTask`, **not** on next launch", which is two incompatible
   implementations of one behaviour depending on which file a session read.
   The resolution is both, for a specific reason: `BGProcessingTask` carries no
   execution guarantee, and `.claude/skills/ui.md` forbids showing anchoring
   failure on the main screen — so if the scheduler path is chosen alone and
   never fires, the failure is undetectable by design. The launch drain is also
   the only one of the two that is observable in a test.
9. **One launch-performance assertion** with a budget measured on the real
   device first. A requirement nobody measures is a wish.
10. **Two writers, one file.** Spawn two processes appending to one
    `events.jsonl`, interleave several thousand events, then assert: every line
    parses, no `(lamport, device)` pair appears twice, and each writer's chain
    verifies unbroken from first event to head. §4. Write this before the widget
    ships, not after.
11. **Damaged-log recovery.** Inject a corrupted middle line, and separately a
    `prev` mismatch, and assert the §6 policy: the damaged copy is written
    first, the longest valid prefix replays, other writers' chains are
    unaffected, the app still launches, and nothing is silently dropped.
12. **The signing key survives relaunch.** Two `Signer` constructions across a
    simulated relaunch yield the same `publicKey`. §8. Without this the
    inherited code mints a new key every launch.
13. **Bundle restore round-trip.** A fresh install fed only the exported bundle
    reproduces every achievement bit-identically and verifies every OTS proof.
    §8. This is the test that makes the survival claim true rather than stated.

Deliberately not written, and say so out loud rather than feeling guilty:
SwiftUI snapshot tests (break on every point release, catch nothing a daily user
would not notice within a day), a broad XCUITest suite (slow, flaky, re-asserts
the flow he personally exercises every morning), tests that an `@Observable`
setter sets, mocked `URLSession` asserting a URL was assembled, and a coverage
target. Keep exactly **one** network test, hitting the real OpenTimestamps
calendars, because the failure mode being guarded against is building on an API
nobody ever called.

## 10. Scheduled, and deliberately deferred

Two different things, split because conflating them was a real defect: four rows
below used to sit in the deferred table with "Nothing" as their trigger, under a
heading stating that no trigger means refused. A reader following that rule
would have concluded the week-1 export and the week-4 verifier were refused
features.

### 10a. Scheduled — already committed, no trigger needed

These are decided. They wait on sequence, not on evidence.

| Item | When |
|---|---|
| **Export / import round-trip** | **Week 1.** The insurance policy that turns any future rewrite into a re-projection instead of a reset. Export is a **bundle**, per §8 — not the log alone. |
| **Interactive Home Screen widget** | **Week 2.** Takes the loop from ~3 s to ~0.7 s and is the highest value item per line of code in the project. App Intents must exist first, as substrate. |
| **Weekly anchoring of the event-log head** | **Week 4**, alongside `OpenTimestampsAttestor`, before `CertificateView` can claim anything about the past. The old trigger — "the first time a newly-shipped rule backfills a historical achievement" — reads as distant but is guaranteed to fire on the *first* run of the week-3 engine, which backfills 7-day and 30-day awards over history accumulated since week 1. ADR 0004 states the consequence: without prior weekly anchoring such an award's anchor "proves only June". Needs only a digest and `Calendars`, and is ~52 free submissions a year. |
| **A standalone verifier script** | **Week 4.** ~200 lines, no dependency on the app, shipped in this repository. The mission sentence promises a stranger can check the record without trusting the app; that is not achievable if the stranger must reimplement a hand-written encoder from a document. See `docs/product.md`. |

### 10b. Deferred — each waits on a trigger

Each item states the trigger. **No trigger means it is refused, not deferred,**
and belongs in the non-goals in `docs/product.md`.

| Item | Trigger to build it |
|---|---|
| **Control Center control / Action Button** | The widget has been in daily use for a month **and** the thumb is demonstrably somewhere other than the home screen. "Once the App Intent exists" was not a trigger, it was a permission — every extra entry point is another place the tap path must stay correct and another place a wrong day boundary or a lost write can hide. |
| **`AppShortcutsProvider` Siri phrases** | A Shortcuts automation is actually wanted. App Intents ship in week 2 as substrate for the widget; registering spoken phrases is a separate, user-facing surface that has to be memorised, and the widget already takes the loop to ~0.7 s. |
| **Lock Screen / StandBy widget** | Cheap, same timeline provider. Verify on device whether `Button` is genuinely interactive in accessory families before designing a tap into it; treat as read-only until confirmed. |
| **OpenTimestamps anchoring** | Week 4, after the certificate exists and is sealed locally. Not before — a local seal is already a complete, honest artifact. |
| **Four remaining rule evaluator kinds** | A rule is actually wanted that `streak` and `total` cannot express. Tripwire: wanting a kind with conditionals *inside* it means stop and write Swift, because that is a DSL arriving by accident. |
| **Neutral days (travel-bridged, or declared rest days)** | An eastward flight actually costs a day, or a rest day is genuinely wanted. This is the piece with the least confidence behind it: one event kind and one branch in the fold, for an edge case that fires perhaps twice a year. |
| **Computed rarity** | The certificate itself feels thin in daily use. (The old trigger named a certificate *detail screen*, which is cut — see `docs/product.md`'s surface budget — so the trigger is restated against the surface that actually exists.) Must be a measurement against the user's own history under a *named* model, displayed with the model attribution inline, or not displayed at all. Never an authored tier. |
| **CloudKit sync** | A second device exists and is used. §7. |
| **watchOS app** | A watch is owned. A wrist tap is the genuine one-second interaction and would outrank the widget; it is a whole target and a sync story, so it is deferred deliberately, not dismissed. |
| **GRDB / SQLite** | The replay budget assertion in §6 fails on the reference device. |
| **Log compaction and snapshots** | §6. Measured as unnecessary through at least 10 years × 10 habits. |
| **Soulbound token contract** | The app is in daily use, OpenTimestamps is working, and there is appetite for the learning exercise. ADR 0001 and ADR 0004. Explicitly not on the critical path — if this limb is never built, Compass is still a complete app with a Bitcoin-anchored record. |
| **Smart account, passkeys, ERC-4337** | Only if the token contract is built. ADR 0003. |
| **Retroactive backfill of a past day** | The app has been in daily use for a month and a forgotten day has actually cost something. It is not in v1: it is the only interaction in the app that needs a date, a scroll and a decision, which makes it strictly more complex than every screen in the MVP combined, and it would land on or behind the 28-dot spine — turning the one display element on the launch screen into a control. If it is ever built it needs, in writing first: an explicit surface, an explicit reach limit in days, and a guarantee that it is unreachable from the launch path. The `source_live` / `source_backfill` partition in the protocol stays REQUIRED regardless, because it is inside the digest and cannot be added afterwards. |

## 11. Build order

Chosen so that no stage can take the project down with it, and so that daily use
begins before anything interesting is attempted.

- **Week 1a — something tappable, on the phone, the first day.** `Day`, `Event`,
  `project()`, the synchronous journal appending to a plain file, `TodayView`,
  four habits seeded in the bundle with their names already set — Move, Read,
  Build, Reflect, chosen by the owner on 2026-07-31 and listed in
  `AppComposition.seededHabits`. Install it. Use it. Nothing else.
- **Week 1b — the encoding, once it is being used.** The hand-written canonical
  byte encoding, `content_hash`, `prev` chaining, the encoding-stability test,
  the shard-invariance and replay-parity tests, the truncation test, the App
  Group move, `actor EventLog`, the snapshot cache, and export as a bundle.
  Entry condition: the app has been opened three days running.
- **Week 2** — App Intents as substrate, then the interactive widget. Same
  append API, zero storage change. The second writer identity and the
  two-writer test (§4) ship **with** the widget, not after it.
- **Week 3** — rule specs, the evaluation engine, `CertificateView`, sealed
  locally with the enclave key only.
- **Week 4** — `OpenTimestampsAttestor`, weekly log-head anchoring, the
  standalone verifier script. The certificate gains a line of text; nothing else
  in the app changes.
- **Later, no deadline** — Control Center control; the chain limb behind the
  same `Attestor` port; watchOS.

The ordering rule that matters more than the order: **the daily loop must be in
daily use before anything cryptographic is built, and everything cryptographic
must be additive behind a port.**

### Why 1a and 1b are split, and the one escape hatch that permits it

§3 calls the canonical encoding the one irreversible early decision, and that is
true — of everything downstream of a signature. It is not true on day one, and
this document should not overstate it, because the overstatement is what put an
irreversible cryptographic commitment at item three of day one for an author
with 58 repositories that died on their creation day. That is the highest-risk
possible ordering and it is the exact anti-pattern `docs/product.md` claims the
plan avoids.

The refutation is already in the corpus. ADR 0002 makes `events.jsonl` the only
non-rebuildable file *of its tier*, and `docs/product.md` makes a rewrite "a
re-projection". A week-1a log written without `prev` holds the same facts as a
chained one. So:

> **The one-time `reproject` escape hatch.** Before the first signature is ever
> computed, the log may be replayed once into a freshly chained log — same
> events, same order, `content_hash` and `prev` computed for the first time.
> The old file is kept as `events.jsonl.pre-chain`.

This hatch may be used **exactly once**, and it closes permanently the moment
anything is signed — which cannot happen before week 3, and cannot be published
before week 4 plus the 72-hour window. After that point the encoding is
irreversible in the full sense and §3 governs without exception.

Stated this way, nothing in week 1 has to be undone in week four, which is what
`docs/product.md` promises. What is deliberately **not** relaxed: the encoding
still lands in week 1, not week 2, and it still precedes anything cryptographic.
The infrastructure ambition is intact; only the ordering within the week moved,
so that the first session ends with a tappable app rather than a digest test.
